# Кукареку Онлайн — витрина и личный кабинет

Отдельный frontend для `webapibackend`. Код backend не изменяется. Next.js 16.3.8, React, TypeScript strict, App Router, SCSS Modules, TanStack Query, React Hook Form, Zod, classnames. Package manager — npm; версии зафиксированы в `package-lock.json`.

## Запуск

```sh
npm ci
cp .env.example .env.local
npm run dev
```

Frontend: http://localhost:3001. Backend по умолчанию: http://127.0.0.1:3000. `BACKEND_URL` задаёт origin без `/api/v1`: серверный адаптер добавляет этот префикс ко всем запросам к Nest. Для production задайте `SESSION_SECRET` (64 hex-символа, `openssl rand -hex 32`), `BACKEND_URL` и `APP_ORIGIN` (точный HTTPS origin витрины, без завершающего `/`). Затем `npm run build && npm start`. HTTPS обязателен для production cookies. Не запускайте несколько реплик без общего хранилища сессий/блокировки refresh: текущая координация ротации работает в одном Node.js процессе. В development ключ генерируется в памяти, поэтому перезапуск сервера завершает локальные сессии.

Backend должен быть доступен серверу Next.js. CORS между браузером и Nest не нужен: браузер обращается к `/api/v1/*` на origin витрины. Не направляйте `BACKEND_URL` на сам frontend.

## Что реализовано

| Маршрут                | Назначение                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------ |
| `/`                    | Витрина с существующим логотипом, преимуществами, живыми тарифами и инструкцией      |
| `/pricing`             | Тарифы из API, цены из копеек                                                        |
| `/login`, `/register`  | Формы, валидация, ошибки, сохранение безопасного `next`                              |
| `/checkout/[tariffId]` | Состав тарифа, итог, продолжение после входа, честное состояние недоступности оплаты |
| `/app`                 | Подписка, использование подключений, первые шаги                                     |
| `/app/connections`             | Список устройств, скачивание и отзыв с подтверждением                                |
| `/app/connections/new`         | Страна → название → создание → скачивание/инструкция                                 |
| `/app/connections/[id]/setup`  | Инструкция для конкретного устройства                                                |
| `/app/subscription`    | Snapshot условий подписки, срок, лимиты                                              |
| `/app/help`            | Инструкции для iOS, Android, macOS, Windows                                          |
| `/app/account`         | Email текущего входа и logout                                                        |

`/app/*` показывает данные только после проверки сессии через backend, иначе возвращает на login с исходным путём. Кабинет, checkout и auth-страницы исключены из индексации. Guard — UX, а не security boundary: BFF проверяет сессию, а Nest проверяет авторизацию и бизнес-правила при каждой операции.

## Структура

```text
src/app/         маршруты, metadata, общий layout, BFF route handler
src/api/         типы ответов, HTTP-клиент, сервисы, query keys, PaymentService
src/server/      доступ к Nest и зашифрованная серверная cookie
src/features/    витрина, тарифы, auth, кабинет, устройства, подписка, onboarding
src/components/  Brand, PublicShell, Providers, Button, ActionLink,
                 ConfirmDialog, ErrorState, EmptyState, Skeleton
src/config/      редактируемые инструкции подключения
src/lib/         правила лимитов, форматирование, ошибки, analytics adapter
assets/source/   исходный логотип (не публикуется)
 tests/          unit-тесты, Playwright-сценарии и изолированный тестовый upstream
```

Response DTO сверены с `src/common/dto.ts`, контроллерами/сервисами и `prisma/schema.prisma` backend. Swagger описывает входные DTO, но не полные response schemas, поэтому response types записаны вручную. Секреты нод и админские API в клиент не попадают. BFF дополнительно исключает из ответа профиля `clientName`, `lastError`, `userId`.

## Реальные методы backend

| Метод                                     | Использование                            |
| ----------------------------------------- | ---------------------------------------- |
| POST `/api/v1/auth/register`              | Регистрация `{email,password}`           |
| POST `/api/v1/auth/login`                 | Вход `{email,password}`                  |
| POST `/api/v1/auth/refresh`               | Ротация `{refreshToken}`                 |
| POST `/api/v1/auth/logout`                | Отзыв текущей сессии                     |
| GET `/api/v1/tariffs?limit=100&offset=…`  | Публичные тарифы, загрузка всех страниц  |
| GET `/api/v1/me/subscription`             | Текущая действующая подписка или null    |
| GET `/api/v1/profiles?limit=100&offset=…` | Устройства, загрузка всех страниц        |
| GET `/api/v1/profiles/:id`                | Подключение для инструкции               |
| POST `/api/v1/profiles`                   | Создание `{nodeId,deviceName}`           |
| DELETE `/api/v1/profiles/:id`             | Отзыв подключения                        |
| GET `/api/v1/profiles/:id/config`         | Оригинальный `.ovpn`, без преобразования |

`/api/v1/session` — BFF-адаптер: проверяет access token чтением `/api/v1/me/subscription` и возвращает состояние входа/email. `/api/v1/locations` проксируется в backend с Bearer-токеном, проверяет формат и возвращает только id, countryCode, countryName, city. Allowlist BFF не пропускает `/api/v1/admin/*`.

## Auth и безопасность

Nest возвращает access/refresh tokens в JSON, native HttpOnly flow в нём нет. BFF забирает токены, шифрует AES-256-GCM и хранит в HttpOnly, SameSite=Lax cookie (`Secure` в production). JavaScript не получает токены; localStorage не используется. TTL cookie не продлевает 30-дневную сессию backend. Ошибка расшифровки/истечение означает отсутствие сессии.

Первый 401 запускает единственный refresh для конкурентных запросов в клиенте, затем запрос повторяется один раз. Сервер объединяет конкурентные refresh одного токена в течение 10 секунд. Неуспешная ротация удаляет cookie; клиент очищает query cache и возвращает к login. Logout отзывает refresh на backend, затем удаляет cookie и cache; если backend недоступен, показывает ошибку вместо ложного успеха. Мутации требуют совпадения Origin с `APP_ORIGIN` или origin текущего Host. Необходимо настроить доверенный Host на reverse proxy.

Пароли: 12–128 символов, email ≤254. Имя устройства: 1–100 после trim. Токены, пароли и конфигурации не логируются. `.ovpn` отдаётся с `no-store`, скачивается как Blob с именем из Content-Disposition, не показывается в DOM и не сохраняется в storage.

## Создание, лимиты и статусы

Создание использует реальный POST. Фронтенд не считает устройство активным заранее. После любой завершившейся мутации обновляются profiles/subscription, включая ошибки с неопределённым исходом. `CREATING`/`REVOKING` и `FAILED + needsReconcile` опрашиваются каждые 5 секунд. Остальные данные обновляются каждые 30 секунд и при возврате фокуса.

Использование лимита повторяет backend policy: `ACTIVE`, `CREATING`, `FAILED + needsReconcile`. `REVOKING` лимит не занимает. `REVOKED` скрыт. Скачивание разрешено только для ACTIVE при действующей подписке. Удаление требует native dialog с клавиатурным focus trap; промежуточные статусы блокируют повторные действия.

У backend есть `profileLimitOverride`, но нет пользовательского endpoint, чтобы его прочитать. Поэтому интерфейс показывает лимит snapshot и объяснение при его достижении; окончательная проверка остаётся за backend. Он не запрещает попытку для пользователя с возможным увеличенным индивидуальным лимитом. Все ошибки лимита/ноды/подписки централизованно переведены в пользовательские сообщения.

## Ограничения фактического backend (без fake production logic)

1. **Нет payment/order API и пользовательского создания/продления подписки.** Checkout показывает условия и недоступную оплату. `PaymentService` имеет `available: false` и явную ошибку. Он не выдаёт подписки и не вызывает admin endpoint. Полный путь «оплатил → подписка активна» требует реализации backend. При появлении реальной подписки dashboard предлагает добавить первое устройство.
2. **Локации поступают из `GET /api/v1/locations` бэкенда.** Авторизованному пользователю доступны включённые ONLINE-ноды со свободной ёмкостью. Учитываются ACTIVE, CREATING и FAILED с needsReconcile. Статический список локаций больше не используется. При нескольких нодах страны выбирается первая доступная из стабильного серверного списка. При создании профиля сервер повторно проверяет доступ и ёмкость под блокировкой. Недоступная нода исчезнет из выбора; для прежнего устройства её название может быть недоступно.

3. **Нет пользовательского `/me` (email, status, ban, effective limit).** Email показан из успешно подтверждённого входа в зашифрованной сессии. `USER_BANNED` узнаётся только из ответа создания/скачивания: после него раздел подключений становится недоступным, logout и помощь доступны. До такого ответа и после новой загрузки страницы frontend не может достоверно узнать бан. Для состояния блокировки сразу при входе backend должен отдать user status/entitlement. Внутренние admin metadata не запрашиваются.
4. **Нет пользовательской истории подписок.** `/api/v1/me/subscription` исключает истёкшие подписки и возвращает null. Нельзя достоверно различить новый аккаунт и истёкшую подписку или показать прежнюю дату. UI это явно учитывает. EXPIRED/CANCELLED/истечение времени также обрабатываются, если такой snapshot уже есть в cache/будет возвращаться API.
5. **Нет изменения пароля/удаления аккаунта.** Фиктивных форм и endpoint нет.
6. **Неизвестный исход создания при потере сети.** API не принимает idempotency key. Автоматического retry мутации нет; перед повтором следует проверить список устройств. Frontend не может гарантировать exactly-once при потере ответа.

Локальный backend при проверке 03.10.2026 ответил 200 на `/api/v1/health`, а `/api/v1/tariffs` вернул `[]`. Его данные не менялись; для рабочей витрины администратор должен создать/опубликовать тарифы и настроить реальные локации.

## Проверки

```sh
npm run typecheck
npm run lint
npm test
npx playwright install chromium
npm run test:e2e
npm run build
```

Playwright поднимает отдельный `tests/fixtures/backend.mjs` на 4321 и Next на 3001. Тестовый upstream не используется командами `dev`, `build`, `start`. Тесты проходят реальный BFF, encrypted cookies и пользовательский интерфейс; не подменяют браузерный API. Не запускайте обычный dev server одновременно с e2e.

Покрытие: тарифы из API; auth validation/login/register/return URL; отсутствие подписки/активная/истёкшая; лимит; создание/ошибка ноды; скачивание и точное содержимое файла; инструкция; отмена/подтверждение удаления; бан/logout; refresh; запрет cross-origin записи и admin proxy. Responsive: 375, 430, 768, 1024, 1440, 1920px, скриншоты landing/devices в `test-results/`.

Полноценная покупка и создание подключения на настоящей ноде не тестировались: payment отсутствует, тестовый пользователь/подписка/нода не предоставлены. Unit/e2e fixtures не являются подтверждением работы реального серверного агента.

Ответ виден по секретной ссылке тикета, email-рассылки нет. Хранилищу нужен постоянный диск; не размещайте его на ephemeral/serverless filesystem.
